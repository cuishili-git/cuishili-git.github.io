实战项目

我用 PyQt6 + 视觉大模型做了一个照片型 PDF 翻译器（附三个调试深坑复盘）

需求：手头有一堆照片型 PDF（扫描件/图片型，无文本层），想翻译成 Word，还要求公式能双击编辑、表格还原。市面上的工具要么只处理文字型 PDF，要么公式变图片。于是自己动手写了一个。

最终效果：拖入一个 PDF，程序逐页渲染成图片 → 并发调用视觉大模型 → 组装成 docx。196 页的文档也能跑（虽然第一跑就把我 education 了一遍，后面细说）。

一、整体架构

四个关键决策：

决策点 方案 理由
逐页 vs 整本 逐页独立调用，不传上下文 可全并发、失败重试便宜、token 省一半以上；上下文永不超长
中间格式 让模型输出结构化 JSON 而不是 Markdown block 类型可控（heading/para/table/formula），纯 Markdown 表格和公式容易碎
模型 OpenAI 兼容的视觉接口（智谱/通义/豆包/方舟都行） 只要支持 image_url base64 就能接，换厂商改两个配置项
公式 LaTeX → MathML → OMML 嵌入 Word 产物是原生公式对象，Word 里双击可编辑，不是图片

二、坑一：接口地址拼接出 404，196 页全灭

第一跑，196 页全部失败：

看 URL 就明白了：用户填的地址带了个 /responses 后缀，程序又在末尾拼 /chat/completions，两个一叠加就成了不存在的路径。更隐蔽的是，程序每次点开始都会把界面上的值回写进配置文件，改配置文件对已经开着的窗口不生效——我修了一版配置，用户一点开始又被旧值覆盖了。

教训有两条，代码上各落了一处：

  1. 对输入做规整，而不是要求用户填对。/responses、/completions、/chat/completions、裸根地址，四种填法都收敛到同一个端点。
  2. 报错要带服务端返回体。原来只有 requests 默认那句 404 Client Error，改成 HTTP {code} {url} → {body[:300]} 后，是地址错、模型名错还是 key 错，一眼可见。

三、坑二：196 页失败却重试了 784 次

第二个问题是止损缺失。每页失败后重试一次，196 页 × 2 = 392 次请求，全部注定失败，日志滚了好几分钟。配置错误是”全体页面共享”的错误，不该按页重试。

解法：连续失败计数 + 自动熔断。

注意用「连续失败」而不是「累计失败」：正常翻译中个别难页失败重试是合理的，累计计数会误伤。

四、坑三：QSpinBox 隐藏按钮后，数字不渲染了

GUI 侧的坑。给参数输入框去掉了 QSpinBox 自带的上下箭头（QSS 下渲染成怪异竖条）：

结果离屏截图里框是空的——value() 明明是 4，text() 也返回 “4”，就是不画出来。抓了 3 倍放大图确认：这是 Qt 在 NoButtons 模式下编辑区布局的老毛病。

解法：不跟 QSpinBox 纠缠，直接换成 QLineEdit + QIntValidator：

损失了滚轮步进，换来了所见即所得。调试 GUI 的经验：先抓部件级放大截图，再下结论，很多”没显示”其实是”画了但看不见”。

五、验证：真实调用跑通

修完地址后，用一张 400×200 的测试页做了端到端验证（成本几分钱）：

翻译、公式、结构全部正确。技术栈清单：

组件 选型
GUI PyQt6
PDF 渲染 PyMuPDF（新包名 pymupdf，旧名 fitz 已废弃）
模型调用 requests + OpenAI 兼容接口，线程池并发 4
docx 组装 python-docx + latex2mathml + mathml2omml

六、小结

三件事值得记住：

  1. 对接第三方 API，永远对用户输入做规整，报错永远带上响应体；
  2. 批处理要有熔断，”连续失败”是识别配置错误的最可靠信号；
  3. Qt 控件反直觉行为，用最小复现 + 部件级截图排查，别信”值在就行”。
