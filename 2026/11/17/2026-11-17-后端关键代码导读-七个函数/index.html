读懂这 7 个函数，就摸清了 1.4 万行后端代码

上一篇画了地图，这篇直接拆代码。

选这 7 个函数的标准是：删掉它们，平台就跑不起来。每个都给出所在位置、真实代码、这段代码在防什么坑。看完你应该能自己动手加一个”新设备类型”或”新算法产品”，不需要问人。

① main() —— 只做装配，不做业务

位置：src/main.cpp:113

新手最容易在这里迷路，因为它有 200 行。但它其实只干一件事情：按固定顺序把零件装起来。

顺序不能乱，原因很实在：

  • 第 3 步必须在第 4 步之前。基线 DDL 只建新库缺的表，升级脚本负责给老库补列。反过来的话新库里会出现”升级脚本给一张还不存在的表加列”的报错。
  • 第 6 步必须在第 7 步之前。hook_impl 读数据走缓存，缓存没加载完就注册，第一次请求会拿到空结果。
  • 第 9 步的 lambda 里有一句特判，是踩过坑加的：

snapshot（抓图）不属于任何一个 worker。MIPI 摄像头、ONVIF 摄像头都要抓图，如果塞进各自的 worker，两边就要各写一份”从 H.264 缓存里解一帧”的代码。所以它被提到平台层，成为所有摄像头设备的公共 service。

② PlatformHook::call() —— 所有非 CRUD 业务的总开关

位置：src/app/hook_impl.hpp:161

七行字符串比较，撑起了整个平台的非 CRUD 业务。加新功能就在这儿加一行。

为什么不让路由直接调 DeviceManager？因为路由一旦认识 DeviceManager，下一步就会认识 json 里每个字段的含义，再下一步就会在里面写 if-else 业务判断——这是上一版代码失控的起点。现在路由只有 67 行（routes/crud.hpp），因为它真的只做 HTTP。

HookReply 里的 status 直接就是 HTTP 状态码（200/400/404/500），路由层原样透传，不做二次翻译。少一层翻译就少一处”接口返回 200 但 body 里 code=500”的坑。

③ WorkerManager::control() + build_ctx() —— 三行代码分出所有协议实现

位置：src/core/worker_manager.hpp:119

impl_class 是 tki_product 表里的一列。产品是 ONVIF 就是 onvif，是 MIPI 就是 mipi，是算法就是 yolo_region。设备属于哪个产品，就用哪个产品的实现类，一行 if 都不用写。

build_ctx() 做的事：设备行 + 产品行从内存缓存取（零 SQL），属性快照查一次库。装好之后交给 worker：

worker 里读配置就是 dc.attr("ip", "192.168.1.64")，写状态就是 dc.set_attr("last_result", "ok", err)。它看不到 SQL，也摸不到数据库。这就是为什么新增一种摄像头协议只需要写一个 259 行的头文件。

实现类的注册也很有意思，在文件末尾：

静态对象在 main() 之前就跑完了构造函数，main 里不需要 new 任何 worker。而且登记不等于实例化——库里扫描到有启用产品用了这个 impl_class，才真正 new 出来。

④ StreamSpec::pipeline_desc() —— 一条管线字符串决定视频怎么出

位置：src/core/stream_hub.hpp:68

两个知识点值得单独记：

  1. 出口必须统一成 Annex B。rtspsrc 出来后默认是 avc（长度前缀），mpph264enc 出来是 byte-stream，不统一的话前端要处理两种格式，jmuxer 会直接报错。所以两条路都用 h264parse ! video/x-h264,stream-format=byte-stream,alignment=au 收口。
  2. MIPI 那条不写死宽高。库里配的分辨率和 sensor 实际能出的经常不一致（库里写 1500，驱动实际 1568），写死会让 caps 协商静默失败——不报错，就是没有帧。真实分辨率改成从首帧 caps 读回。

⑤ Stream::dispatch() 与 ws::Conn::enqueue() —— 花屏的根因和修法

位置：src/core/stream_hub.hpp:611 + src/core/ws.hpp:173

这是全项目最有价值的一段代码，因为它对应一个排查了整整一天的花屏问题。

旧做法（错的）：

新做法：

每个连接一条 sender_loop() 线程，只有它碰 send()。推流线程只做入队，永远不会被某个慢观众卡住。

加上 raw_send() 里的总时间预算（单帧超 500ms 判死，不只是 SO_SNDTIMEO 的 per-call 超时）——因为慢客户端每次只挤几个字节，per-call 超时永远不触发，dispatch 就被永久拖住了。

现象和根因的对应关系值得记牢：

现象 根因
看着看着花屏，刷新就好 共享 appsink 丢了编码帧，参考链断裂
只有一个人看也花 那个人的浏览器在后台被节流，send 阻塞
多人看时互相影响 推流线程被最慢的那个观众拖住
花屏后不恢复 关节帧被丢，等不到下一个 IDR

⑥ Stream::snapshot() —— 抓一帧，顺便解决图像变形

位置：src/core/stream_hub.hpp:355

抓图不是”停推流去截图”，而是用推流线程缓存的最近 60 帧 H.264 起一条临时解码管线：

这行的 pixel-aspect-ratio=1/1 是血泪教训。YOLOv5 训练时用的是 letterbox（等比缩放 + 补黑边），推理时如果直接拉伸到 640×640，人就被横向拉扁，置信度会明显偏低——实测同一个人从 0.55 掉到 0.43。

videoscale add-borders=true 按理说就该补黑边，但板上的 videoscale 会用”非方像素”（PAR=11/9）来保住显示比例，buffer 内容照样是拉伸的，黑边根本不画。必须把 PAR 锁死成 1/1，它才老实补边。板端 gst-launch 实测黑边区域均值 4.8/1.8，中心区域正常。

⑦ YoloRegionWorker::invoke() —— 算法判定的四步顺序

位置：src/workers/yolo_region/yolo_region_worker.hpp:163

顺序不能换。先区域后标签，会出现”框在区域内但标签不是目标”也算命中；先标签后区域才对。

还有一个容易误读的设计：两个置信度。

  • detect_confidence（默认 0.25）：传给推理进程的粗筛阈值，越低漏检越少，但框更多、后处理更慢。
  • confidence（默认 0.5）：平台侧细筛，决定报不报警。

所以看到 dropped score 0.43 不要以为模型坏了——它只是被平台侧 0.5 的阈值挡下了，dropped 里明确写了 reason: score_below。弱目标（远距离的人、半遮挡）给 0.29 不点灯，是设计正确，不是 bug。

排障时看这四个数就够了：raw_count=0 是模型或帧的问题，label_kept=0 是阈值问题，count=0 是区域画错了。

⑧ FlowEngine::run() —— 流程节点就是三次函数调用

位置：src/app/flow_engine.hpp:53

关键在 hook().call("device.control") 这一行：流程执行和网页手动点击走的是完全相同的入口。所以网页上能手动触发的服务，配进流程就能自动跑；流程里跑不通的，网页上一定也跑不通。不存在”自动化专用路径”这种东西。

模板渲染 {{prev.count}} 是纯字符串替换，所以数字也会变成字符串。这就是 yolo_region_worker 里要写 lr_int() / lr_num() 做类型转换的原因——直接 json.get<int>() 会抛异常。

新手最容易踩的五个坑

坑 现象 正确做法
在路由里写业务 越写越乱，改一处崩一片 只在 hook_impl::call 加 action
worker 里调 DbManager 编译过、运行也行，但破坏了分层 用 dc.attr() / dc.set_attr()
在数据面线程里做阻塞 IO 一个人卡，所有人一起花屏 队列 + 独立发送线程
改 CREATE TABLE 不改升级脚本 新板子正常，现场板子缺列 基线不动，写 V0xx.sql
用 gst_buffer_new_wrapped 包 DRM 内存 free(): invalid pointer 直接 abort 用 gst_memory_new_wrapped，destroy 传 NULL
