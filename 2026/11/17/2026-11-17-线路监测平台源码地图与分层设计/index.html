实战项目

线路在线监测平台源码地图：1.4 万行代码怎么分层，新手从哪读起

这个项目最终跑在一台飞凌 OK1126B-S 开发板（RV1126B，aarch64）上，做的事很具体：接一路 MIPI 摄像头，把画面推到网页上实时看，同时每隔一段时间用 NPU 跑一次 YOLO 检测，命中目标就点亮一个 GPIO 报警。

代码量不大，但第一次打开目录很容易迷路——46 个头文件、5 个独立进程、4 个数据库表族、1 个 Vue3 前端。这篇先把地图画清楚：谁是入口、谁只能单向依赖谁、一次点击从浏览器走到硬件要经过哪几层。

一、先记住三台机器

角色 位置 装什么 你在这上面干什么
开发机 Windows 前端源码 vue3/、后端源码副本 改代码、看报错、写页面
编译机 Ubuntu VM（~/forlinx/my） 交叉工具链 + 全部后端源码 + 飞凌 SDK 编译出 aarch64 二进制
板子 192.168.1.232 只有二进制、前端 dist、数据库、日志 跑、验收、看日志

没有在板子上编译这回事。板子上的 8G eMMC 只有 3 个 G 可用，编译一次 GStreamer 相关代码要 20 分钟以上，所以一切二进制都在 VM 上交叉编译好，scp 推过去。这条规矩定死了，后面所有流程都围绕它。

二、板上实际跑着 5 个进程

为什么把推理拆成独立进程？因为 RKNN 的 NPU 上下文一旦崩了会把整个进程带走。2026-11 之前推理还在主平台里，模型一异常整个网页就 502。拆出去之后 rknn_inferd 挂了只是算法报警失效，看视频不受影响，watchdog 会单独把它拉回来。

为什么 3A 是独立守护？rkaiq 的 API 不是线程安全的，而且它的初始化要等 ISP 媒体图建好。混在业务进程里，一重启业务进程就得重走一遍 ISP 初始化，中间黑屏 10 秒。分开之后参数调整是”发命令”，不碰业务。

三、主平台的分层：三层单向依赖

这是整套代码最重要的设计，理解了它就不会写错代码：

三条铁律，违反了代码就会被 review 打回：

  1. 路由文件里不许出现 SQL、表名、模型。只能 hook().call("device.control", args)。
  2. worker 实现类里不许出现 DbManager。要读配置就用 dc.attr("ip")，要写状态就用 dc.set_attr()。
  3. DbManager 只被 DeviceManager 和 hook_impl 使用。

好处是具体的：换数据源只改一个文件；单元测试装个假 hook 就能跑路由；新人改业务只碰 hook_impl.hpp，不会误伤 HTTP 层。

四、目录速查（按你真正会改的频率排序）

前端 vue3/src 约 4400 行，10 个页面 + 3 个组件，最大的 H264Player.vue 549 行（WebSocket 收流 + MSE 解码）。

五、三张数据流，看懂就懂 80%

流 1：网页改一个参数（配置类）

配置类表（产品、设备、通道、码流）全部常住内存，DeviceManager::load() 在启动时一次性读进来。之后所有 list 接口都是内存过滤，不走数据库——这是网页秒开的原因。

流 2：网页看实时视频

关键点：推流线程绝不直接 send。2026-11-10 排查了一整天的”看十几分钟就花屏”，根因就是早期版本在推流线程里对每个观众阻塞 send——任何一个观众卡顿（切标签页、WiFi 抖动），推流线程就停在 send 上，共享的 appsink 开始丢编码帧，丢掉的是别人的参考帧，于是所有观众一起花屏。现在每个连接一条发送线程 + 4MB 有界队列，超限只踢那一个连接。

流 3：定时跑一次算法（流程）

划重点：算法设备自己截图，不再需要在流程里拖一个”摄像头截图”节点。这是 2026-11-10 的简化，减少一次人工配置错误的机会。

六、四个”反直觉但必须这样”的设计

设计 直觉做法 实际做法 为什么
传帧给推理进程 传内存指针 / 传整帧字节 传 dma-buf fd（SCM_RIGHTS） 指针跨进程无效；传 1.2MB 字节每帧多一次拷贝，NPU 还得再拷一次
打开 MySQL 式的连接池 每请求建连接 单例 + 读线程/写线程各一条队列 SQLite WAL 下写必须串行，加连接只会撞 SQLITE_BUSY
实时视频用 RTSP 起 rtsp 服务端 直接 WebSocket 发裸 H.264 板子没装 mediamtx，浏览器也不认裸 RTP；WS 一条通道同时能发 JSON 控制消息
结构变更 改 CREATE TABLE 只改基线 DDL，增量放 sql/upgrade/V0xx.sql 现场板子的库里有数据，重建表就全丢了；版本表记账可以反复执行

七、给你的阅读顺序

不要从头读。按这个顺序，每步都能跑起来验证：

  1. main.cpp —— 只看 113~213 行，看清楚启动顺序：开库 → 建表 → 升级 → 装 hook → 注册路由 → 监听。
  2. 打开网页点一次「设备列表」，对照 routes/crud.hpp → hook_impl.hpp::list → device_manager.hpp::rows，把这条链路走通。
  3. 读 core/entity.hpp 和 hook_impl.hpp::register_default_entities()，理解”实体名 → 表”是怎么注册的。
  4. 读 workers/gpio/gpio_worker.hpp（259 行，最短的实现类），理解 invoke() 这个唯一入口。
  5. 读 app/flow_engine.hpp::run()，理解流程节点怎么变成 hook().call("device.control")。
  6. 读 workers/yolo_region/yolo_region_worker.hpp，理解算法产品的四步判定。
  7. 最后才碰 core/stream_hub.hpp（856 行，最难）和 core/osd_service.hpp（600 行，涉及 RGA 和 ISP）。

前 6 步都是纯业务逻辑加 SQL，不需要懂 GStreamer、不需要懂 NPU、不需要懂 ISP。这是刻意的：这套代码的分层就是为了让 80% 的需求不需要碰那 20% 的硬骨头。

下一篇会把上面第 1、4、5、6 步对应的函数逐个拆开讲，配上真实代码和踩坑理由。

附录 B：完整推流流程，每一环涉及哪个文件

从 MIPI 摄像头的光子到浏览器里的像素，一共 9 环。整个数据面只涉及 6 个后端文件，其余都是配置来源（查一下就退场）。

每一环的细节：

环 文件（行号） 发生什么
入口 app/routes/stream_routes.hpp（51 resolve_spec / 162 路由体） 浏览器 GET /api/stream/:session?device_id=...&channel=1&stream=main。查 DB 里的通道/码流属性，决定 kind：ONVIF=0（rtsp url）/ MIPI=1（/dev/video 设备）。然后 ws::accept 完成 101 升级、Hub::acquire 拿共享 Stream
拼管线 core/stream_hub.hpp（68 pipeline_desc()） MIPI：v4l2src ! ... ! mpph264enc name=osdenc ! appsink max-buffers=5 drop=true（硬编码，零 CPU）；ONVIF：rtspsrc location=... protocols=tcp latency=200 ! 解码 ! 缩放 ! mpph264enc ! appsink（因为网页不能播相机的原始 H.264 参数集，要转编一次）
起管线 core/stream_hub.hpp（220 附近 start() / 244 挂 probe） gst_parse_launch → 找到 appsink name=vsink → 在 osdenc 的 sink pad 挂 osd_probe → 起独立线程跑 loop()
OSD 叠加 core/osd_service.hpp（146 osd_probe 在 stream_hub 里，blend 在 osd_service） 每一帧编码前，把 FreeType 光栅化的文字（时间戳/标题）SRC_OVER 进 NV12 帧的 Y/UV 平面。probe 首帧记录分辨率并注册通道
拉帧分发 core/stream_hub.hpp（521 loop() / 467 nal_type / 490 找 SPS 拼 codec 串） app_sink_pull_sample 拿到 Annex B 数据。观众初次接入时先发一帧文本 init（{"type":"init","codec":"avc1.xxxxxx",...}），再发二进制 [1B flag][8B pts][NALU]；只把 SPS/PPS/IDR 之前的部分原样转发，不做转码
发送 core/ws.hpp（173 enqueue / 232 sender_loop / 214~216） 推流线程只入队，绝不 send。每连接一条 sender 线程从 4MB 有界队列取数据发送；队列超限判定该连接假死，只踢它一个，不影响别人
HTTP 底座 core/minihttp.hpp TCP 监听 + HTTP 解析 + WebSocket 101 升级握手（SHA1+base64），升级后的 fd 移交给 ws::Conn
播放 vue3/src/components/H264Player.vue（138 feedMse） 收 init 文本帧解析 codec → jmuxer 把 Annex B 封 fMP4 → MSE 喂 <video>。HUD 里有延迟显示（buffered.end - currentTime），卡顿时看它就知道是缓冲在涨

配置从哪来（只查库不参与数据面）：resolve_spec 读的通道/码流属性由 core/device_manager.hpp 缓存提供；ONVIF 相机的 rtsp 地址是当初 workers/onvif/onvif_proxy.hpp::invoke 调 GetStreamUri 存进库的；MIPI 的 /dev/video23 设备号是 workers/mipi/mipi_worker.hpp 写的通道属性。改推流行为只动 stream_hub / ws / stream_routes 三个文件，其他都是旁路。

两个容易踩的坑也在这里标出来：

  1. appsink max-buffers=5 drop=true——缓冲池故意开得很小，推流线程一卡就丢新帧保旧帧。这个设计配合”每连接独立发送线程”才成立：发送线程卡死不再影响推流线程。如果你要在 loop() 里加耗时逻辑，必须想清楚它会让所有观众一起丢帧。
  2. 抓图（snapshot_service）不碰主管线——它用 loop() 缓存的最近一个 H.264 AU 另起一条临时解码管线（stream_hub.hpp 350~380 行），编码主链路上一根手指都不碰。这也是”网页推流”和”算法截图”互不干扰的原因。
