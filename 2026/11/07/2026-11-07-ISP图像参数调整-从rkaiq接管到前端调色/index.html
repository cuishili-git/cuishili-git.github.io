ISP 图像参数调整：从 rkaiq 接管到前端调色

试验平台：Forlinx OK1126B-S / RV1126B 四核 Cortex-A53 / 内核 6.1.141 / OV13855 MIPI 摄像头
日期：2026-11-07

背景：为什么要做这件事

板子上的 MIPI 摄像头（OV13855）推流到前端，画面一直偏蓝。想加亮度、对比度、饱和度、色调四个参数的调节能力，让用户在前端拉滑杆就能调。

听起来很简单——不就是改几个参数嘛。但实际做下来，从方案探索到最终落地，踩了一串坑，推翻了好几次自己的判断。这篇文章把完整过程记下来，希望后来人少走弯路。

第一步：搞清楚能在哪里调

一块板子从 sensor 到前端，数据要经过好几道关卡。能调色彩的位置不止一个，但每个位置的代价和效果完全不同。

方案 调在哪 四参数 代价 进码流 落地难度
rkaiq UAPI2 ISP 内部 全支持 零（硬件） 是 高
IQ json 静态 ISP 内部 全支持 零 是 低，但只能重启生效
GStreamer videobalance 编码前 NV12 全支持 主码流 28.5ms/帧 是 低，一行插件
CSS filter 前端浏览器 全支持 零（客户端算） 否 极低
RGA 硬件 编码前 只有色彩空间转换 硬件 是 做不了这 4 个参数

先说几个容易误判的点：

v4l2-ctl 走不通。在板上执行 v4l2-ctl -l -d /dev/video23，ISP 节点只有 pixel_rate 一个控制项，没有 brightness/contrast/saturation/hue。RK 平台的这些色彩处理全在 rkaiq 里，V4L2 接口不暴露。sensor 的 subdev 只有 exposure、analogue_gain、test_pattern，也没有色彩参数。

RGA 做不了。librga.so 只导出 imcvtcolor/improcess，这是 BT.601↔709、full↔limited range 这类色彩空间转换，没有独立的亮度/对比度/饱和度/色调接口。指望它来调色是常见的误解。

videobalance 太吃 CPU。在四核 A53 上实测，2112×1568 主码流每帧要 28.5ms CPU，28fps 下单核占用约 80%，会掉约 19% 帧率。子码流 720p 只需 8ms，可以用。

所以最终目标是走 rkaiq UAPI2——零开销、进码流、全平台生效。但这条路最复杂。

第二步：librkaiq 控制的是谁

librkaiq.so 是用户态库，同时控制 ISP 和 sensor，但分工很清楚：

ISP 侧：AE、AWB、CCM、Gamma、CGC、HSV 等算法计算出的结果，组合成结构化参数块，通过 rkisp-input-params 视频节点用私有 ioctl 下发给内核 rkisp 驱动，由驱动转成 ISP 硬件寄存器。亮度、对比度、饱和度、色调全走这条路径。

sensor 侧：只有曝光和增益。通过 subdev 的标准 V4L2 ioctl 写 V4L2_CID_EXPOSURE 和 V4L2_CID_ANALOGUE_GAIN，由 ov13855 驱动转成 I2C 寄存器写。

四参数 API 的签名（在 rk_aiq_user_api2_imgproc.h 里）：

level 是 unsigned int，范围 [0, 255]，不是 float，也不是 0~1 的归一化值。

关于对焦：OV13855(CMK-OT2016-FV1) 是定焦模组，不带 VCM 马达。subdev 没有 focus_absolute，设备树里搜不到 lens-focus，dmesg 里也没有 vcm 驱动。IQ json 里的 af_calib/vcm 只是模板字段。所以对焦只能手动拧镜头。

第三步：踩坑——以为能当 client

一开始我在 librkaiq.so 的符号表里发现了 /tmp/UNIX.domain 这样的 unix socket 路径，还有 bind failed, reason: Address already in use 这样的错误串。于是判断：librkaiq 内置了 server/client 模式——第一个调 init 的进程当 server 绑定 socket，后来的进程当 client，通过 socket 转发请求。

这个判断是错的。

去读源码（rkaiq/ipc/socket_client.c:19），发现一行：

这个宏定义着，于是 ClientThreadFunc 走的是 try_accept 分支——每个调用 init 的进程都会执行 unlink + bind + listen 同一个 socket，没有”发现已有 server 就当 client”的降级路径。而 AiqManager_init 是无条件执行的，一定会抢 ISP 的 params/stats 节点。

实测验证：3A server 活着时，forlinx 用户去跑 init → 无法 unlink root 的 socket → bind 失败 → 段错误。

第四步：三条硬约束

撞了几次墙后，总结出三条绕不开的约束：

约束 现象 证据
必须停 rkaiq_3A_server 不停就段错误 3A 在跑时 init → Segmentation fault
必须以 root 运行 非 root 能出流但 AE 不工作 Thread(isp_3a_stats_poll) create fail → 画面全暗
接管后必须重启推流服务 3A 不 attach，画面全黑 3A 需要 stream-on 事件才接管；AE 收敛要约 25 秒

第二条特别坑：非 root 用户（forlinx）能 init 出 ctx，能出流，但 AE 统计线程创建失败，导致画面全暗（Yavg=54）。必须 root 跑才正常。

一个低级错误要记一下：busybox 的 ps 不带参数只显示当前用户的进程。板上的 rkaiq_3A_server 是以 root 启动的，用 ps 看到的是 0 个，以为它没起来，反复 killall + 重启板子，把状态搞得一团乱。查 root 服务必须用 ps -ef 或 ps aux。

第五步：四参数确实生效

用 root 停掉 3A、启动自己的验证程序（aiq_live），调参数后抓流用 ffprobe signalstats 算客观指标：

状态 Yavg U 偏离 V 偏离 码率
3A 正常基线 126.6 +37.3 -32.5 4548
接管后默认 118.4 +45.6 -44.6 4541
setBrightness=200 190.3 +48.1 -53.7 4863
setSaturation=240 118.0 +48.5 -55.2 4720

亮度从 118 涨到 190（+72），饱和度让 U/V 偏离同步放大。接口真实有效。

饱和度标定曲线（白天实测，U/V 偏离值）：

saturation U 偏离 V 偏离 效果
0 0.00 0.00 纯黑白灰度
32 +8.4 -8.5 几乎无色
64 +16.6 -17.4 淡色
96 +25.5 -26.8 正常
128 +31.7 -33.4 标准
192 +38.0 -42.9 浓艳

s=0 时 U/V 恰好等于 128.00，完全灰度，证实 level 直接控制饱和度。

brightness=255 会黑屏：这是一个必须捂住的坑。255 把画面打成全黑（Yavg=16），254 完全正常（Yavg=193.7）。原因是 uint8 溢出。其他三个参数（contrast/saturation/hue）的 255 都正常。

第六步：架构设计

既然”必须 root + 独占 ISP”绕不开，把 librkaiq 直接链进 device_platform 意味着整个业务服务要 root 运行，安全风险太大。所以选择独立守护进程方案：

拆成两个进程的好处：

  • 权限隔离：device_platform 跑在 forlinx 用户，只有 paramd 需要 root
  • 故障隔离：paramd 崩了可独立重启，不牵连前端；device_platform 重启不影响 ISP
  • 未来扩展：要加锐化/降噪/伽马，只改 paramd

第七步：编写 aiq_paramd

aiq_paramd.c 是一个单文件 C 程序，不需要 Makefile，一条 gcc 命令编译。

核心逻辑：

  1. 初始化 rkaiq（sysctl_init → sysctl_prepare → sysctl_start），拿到 ISP 上下文
  2. 创建 unix socket /tmp/aiq_paramd.sock，chmod 666（让 forlinx 用户也能连）
  3. poll 循环等待客户端连接，收到 SET b c s h 就调四个 API，收到 GET 就回读当前值
  4. SIGTERM 时干净 deinit（stop → deinit → unlink socket）

brightness clamp 到 254：收到 255 自动降为 254，防止黑屏。

编译（在虚拟机上）：

为什么单文件不用 Makefile：一个 .c 编译成一个可执行文件，一条 gcc 命令就是最干净的构建系统。多文件项目（比如 device_platform 后端用 CMake 管理 20+ 个头文件）才需要 Makefile/CMake。

参数解释：

参数 作用
--sysroot 指定 SDK 系统头文件和库的根目录
-I.../rkaiq/uAPI2 rkaiq 用户 API 头文件路径
-L -lrkaiq 链接 librkaiq.so
-lpthread -ldl -lm rkaiq 内部依赖的线程/动态加载/数学库

device_platform 侧加了一个 aiq_client.hpp，核心就三个函数：

socket 收发：每次命令都是短连接——连上、发、收、关。

值映射：库表和前端用 0100（50 中性），paramd 用 0254（127 中性）。

转发：拼成 SET b c s h\n 发出去。

三个触发点（在 hook_impl.hpp 里）：

  1. 创建图像参数行时：CRUD create 钩子调 aiq_push_from_row()
  2. 更新图像参数行时：CRUD update 钩子先 get 完整行（因为 PUT body 可能只传了部分字段），再调 aiq_push_from_row()
  3. 服务启动时：aiq_sync_image_params_from_db() 从库读全部 image 行逐行推给 paramd，确保 paramd 重启后参数能恢复

踩过的坑：发命令忘了带 \n。paramd 按换行分帧，没有 \n 就永远等不到完整命令；device_platform 也在等回包，双方死锁。加上 \n 后立刻通了。

第九步：数据库改造——参数挂通道不挂码流

原来的 tki_video_image 表挂靠在码流上（stream_id），每个码流一行。但这有个问题：主码流和子码流共用同一套 ISP，按码流各存一份参数，调主码流时子码流不跟着变，两边会打架。

踩的坑：

  • 脚本里写了 s.stream_type，但表里实际叫 s.stream_name（main/sub），INSERT 失败。更坑的是升级器有 bug——脚本执行失败但版本号照样记录，事务回滚没兜住。排查方法：对比 select * from tki_schema_version（版本号）和 .schema（实际表结构），如果版本记了但表没改，手动删版本记录 + 清残留表 + 修脚本重跑。
  • INSERT...SELECT 的 NOT EXISTS 在同一语句里防重不可靠（同一个通道出现了两行），需要事后用 DELETE WHERE rowid NOT IN (SELECT MIN(rowid) ... GROUP BY channel_id) 清理。
  • 网络相机（大华）的 image 行也会被启动同步推给 ISP。这块板只有一套 ISP，”最后写入者赢”，网络相机的参数会错误覆盖 MIPI 的设置。网络相机的调参应走 ONVIF Imaging，不是本地 ISP，所以把那行删了。

第十步：开机自启

板子重启后必须自动恢复，否则方案就失效了。关键点：原来的 S40rkaiq_3A 会自启 3A server 抢占 ISP，必须禁用。

脚本 状态 作用
S40rkaiq_3A 已禁用（改名 disabled_S40rkaiq_3A，保留可恢复） 原 RK 官方 3A server
S41aiq_paramd 新增（root） 起 paramd + 等 socket 就绪最多 20 秒
S45device_platform 新增（forlinx） 起业务服务 8080

启动顺序铁律：清残留 socket → paramd → device_platform。

S41 为什么要等 socket：S45 起 device_platform 时，它会从库同步参数推给 paramd。如果 paramd 还在 init（约 5 秒），socket 没就绪，同步就连不上，参数推不过去。所以 S41 启动 paramd 后会轮询 socket 文件是否存在，最多等 20 秒才返回，确保 S45 起服务时 paramd 已就绪。

这个竞态踩过——第一次冷启动后 paramd 值是 128（命令行初值）而不是库同步的 127，就是因为 dp 起得太早。

验收

端到端测试：

全程约 8 秒生效，不需要重启任何进程。

冷启动测试（两轮）：

  • paramd 自动起 → dp 自动起 → 8080 监听 → 库里的中性参数（50/50/50/50 → 127/127/127/127）自动同步进 ISP → 画面正常（29.9fps）
  • 3A server 正确不启动（S40 已禁用）

肉眼验证：

  • saturation=0 时画面是纯黑白灰度（U/V=128.00）
  • saturation=200 时色彩明显更浓艳
  • brightness=200 时画面明显更亮（Yavg 从 118 涨到 190）

总结

整个方案的核心决策链条：

  1. 选 rkaiq 而非 videobalance——零 CPU 开销，进码流，全平台生效
  2. 选独立守护进程而非链进业务服务——权限隔离（只有 paramd 需要 root），故障隔离
  3. 选 unix socket 而非 dbus/共享内存——板上没有 dbus，也没有 /dev/aiq_share_mem，socket 最简单
  4. 参数挂通道而非码流——主/子码流共用一套 ISP，按码流存会互相覆盖
  5. 禁用原 3A server 而非共存——rkaiq 上下文全局唯一，没有 client 降级

踩过的坑（按时间顺序）：

  • 以为 librkaiq 有 client 模式，实测段错误
  • busybox ps 不显示 root 进程，误判 3A 没起来
  • 发命令忘了带 \n，双方死锁
  • brightness=255 黑屏（uint8 溢出）
  • 升级脚本引用了不存在的列名（stream_type vs stream_name）
  • 升级器事务回滚有 bug，脚本失败但版本号照记
  • 开机自启竞态（dp 起得太早，paramd 还没就绪）

每一个坑都花了时间排查，但也都留下了实测数据。最终方案经受住了两轮冷启动验证，从前端拉滑杆到画面变化全链路打通。
