从摄像头到网页：一次完整的视频链路拆解

记录一个嵌入式视频平台（RV1126B + GStreamer + Vue3）从「设备接入」到「网页出画」的完整链路，
以及沿途踩过的坑。所有代码与数据均来自实际部署环境，不是示意。

0. 全局视图

整条链路可以切成五段，每段的职责边界很清楚：

阶段 做什么 关键组件 产物
① 设备接入 设备/通道/码流建模 SQLite tsl.db 一条码流配置
② ISP 配置 读写图像参数 deviceControl → Worker → V4L2 / SOAP sensor 参数
③ 拉流编码 采集 + 编码 GStreamer 管线 H.264 Annex B
④ 分发推流 一管线多观众 Hub + WebSocket 二进制帧
⑤ 解码播放 MSE / WebCodecs H264Player.vue 画面

值得先说明的一点：②和③是弱耦合的。ISP 配置通过 REST 走 deviceControl，拉流走
WebSocket，两条路互不阻塞。所以「调参数时画面卡一下」不会互相拖累，但反过来也意味着
改完 ISP 参数不会自动重开流，需要前端自己处理刷新。

1. 设备接入：为什么要有三层模型

很多简单方案是「一个摄像头一个 URL，存个 JSON 完事」。这套系统用了三层，是为了让
同一套代码同时支持 MIPI 本地相机和 ONVIF 网络相机。

关键字段：

表 字段 作用
tki_product impl_class 决定用哪个 Worker，onvif / mipi
tki_product_service code 允许调用的命令名，未声明 → 404
tki_device_attr video_node MIPI 采集节点，如 /dev/video23
tki_device_attr 账号密码 ONVIF 认证用
tki_video_stream width/height/fps/bitrate_kbps/gop 编码参数的唯一来源

踩过的坑：ONVIF 明明加了 set_image_params，前端调还是报错
未实现的服务: set_image_params。第一反应是「物模型没登记」，其实是 worker 的
invoke() 里没有对应分支 —— 这句提示是 worker 层返回的，不是路由层。两者的区别
很重要：物模型没登记 → 路由层 404；物模型登记了但 worker 没实现 → 任务失败 +
未实现的服务。

但 resolve_spec() 从不产生 2，目前是死代码，留着调试用。

key 的拼法是 <channel_id>/<stream_name>，比如 vch_tki_device_1793792600_2_1/main。
同一个 key 全局只有一条管线，这是后面所有复用逻辑的基础。

3. 双链路的分岔点

这是整个系统最容易被误解的地方：MIPI 和 ONVIF 走的是完全不同的处理路径。

这意味着：

  • 想改 ONVIF 摄像头的分辨率 → 去摄像头自己的 Web 页面改，改库没用
  • 想改 MIPI 的分辨率 → 改 tki_video_stream 表，立刻生效

同一个 pipeline_desc() 函数里，kind==0 分支根本不读 width/height，只在
kind==1/2 时才会拼进 caps。

4.4 绕不开的 rkaiq 3A

这是整个项目最反直觉的部分。

rkaiq_3A_server 是一个常驻进程，它每秒都在往 V4L2 写曝光和增益。你手动写
exposure=300，1 秒内就会被它纠正回去。表现形式就是「调完滑块，刷新页面又变回原值」。

更麻烦的是它的副作用：

操作 后果
正常运行时手动写 V4L2 1 秒内被 3A 覆盖
kill 掉 3A 采集管线断流 + ISP 状态污染（出黑白半调点阵）
kill 后恢复 必须重启板子，重启 3A 进程无效

所以正确的做法不是杀进程，而是让 3A 主动停手。项目里做了一个治理脚本：

配套 sudoers 白名单免密（这块板子没有 /etc/sudoers.d，只能直接改 /etc/sudoers

4.5 AE 为什么会「一闪一闪」

排查亮度闪烁时踩的坑，值得单独记一笔。

现象：画面亮度 142 → 108 → 118 → 122 → 159 → 146 → 142 循环，周期约 0.5 秒。

直接读 sensor 曝光才发现根因：

曝光只在两个档位之间硬跳，增益始终是 128 完全没动。

翻 IQ 文件找到原因：

50Hz 抗闪烁强制曝光时间必须是 10ms 的整数倍。这颗 sensor 的行时间换算下来：

  • 1928 行 ≈ 20.5ms ≈ 2 个半周期
  • 2893 行 ≈ 30.7ms ≈ 3 个半周期

中间没有别的档位可选。而 route.time_dot 在 0.03s 处又卡了个上限，曝光到 30ms
不许再拉长，增益通道没被启用 —— 于是 AE 被锁死在这个二选一里，场景亮度又恰好落在
正中间，就永远来回跳。

解法：现场是自然光，关掉 antiFlicker_en，曝光立刻恢复连续可调。

改完实测：

指标 改前 改后
曝光 1928 ↔ 2893 硬跳 2411 → 2380 → 2314 平滑
亮度标准差 13.43 0.15

5. GStreamer 管线

5.1 三条模板

两个细节：

  • drop=true + max-buffers=2：观众卡住时丢帧而不是堆积，避免内存无限涨
  • sync=false：不跟时钟对齐，出帧就推，延迟最低

5.2 分辨率到底是怎么生效的

链路是四段，理解它就能明白「为什么库里的配置有时不生效」：

caps 是「请求」，不是「命令」。 驱动可以拒绝、可以取整。所以代码必须在首帧
从 h264parse 的 caps 回读真实值：

然后 init 帧用 actual_w_ 而不是 spec_.width，前端按真实值初始化解码器。

之前出过的问题：caps 里根本没写 width/height（只写了 format 和 framerate），
v4l2src 就沿用驱动默认值 = ISP 主路径全分辨率 = 3840×2160，而库里配的是
2112×1500。结果编码器按 2Mbps 编 4K 撑不住，每 3~4 帧丢 2 帧，实际只有 19.5fps。

修完的对比：

指标 修复前 修复后
实际分辨率 3840×2160 2112×1568
帧率 19.54 fps 30.02 fps
帧间隔分布 200 次 33ms + 72 次 100ms 418 次全 33.4ms，零丢帧

另外一个坑：宽高比必须和 sensor 原生比例对齐。13855 原生 4224×3136 是 4:3，
所以 2112×1568 成立；库里原来写的 1500 不是 4:3（2112/1500=1.408），比例不对。

5.3 管线错误必须主动 pop

这是最容易写成「静默失败」的地方：

caps 协商失败、设备打不开、缺插件 —— 全部只在这里体现。不 pop 的话表现是
「WebSocket 握手成功、前端连上了、但一帧都没有」，日志干净得像没事一样。

6.3 死流自愈（一次真实的线上故障）

故障现象：ONVIF 摄像头（108）主码流打不开，子码流正常。刷新页面无效，
只能重启服务。

排查过程：

  1. ffprobe 直连摄像头，主/子码流都正常 → 排除摄像头
  2. 板上 gst-launch 手动拉主码流，8 秒落了 4.0MB → 排除网络和管线参数
  3. 板上二进制与虚拟机 build-aarch64 MD5 完全一致 → 排除版本不一致
  4. 看 /api/streams，发现主码流 subs=1 但早就没画面 → 死流卡在表里

根因是两处代码配合出来的缺陷：

于是：主码流失败一次（摄像头忙、网络抖一下）→ 死流永久留在表里 → 后续所有
开播都复用它 → 永远没画面。子码流第一次就成功，所以一直正常。

日志证据链：

修复三处：

文件 改动
stream_hub.hpp 新增 dead_ + alive()；error / EOS / 连续 30 秒无数据 都判死；acquire() 先摘后建；release() 加指针身份校验；新增 notify_dead()
stream_routes.hpp release(spec.key, st.get()) 带身份
H264Player.vue onclose 里补 ws = null（原来不清空，重连判断直接 return）

release 加身份校验是为了防一个边界情况：老观众退出时，如果只是按 key 释放，
会把重建后的新流误杀。

验证方式：用 iptables 真的把网络切断 60 秒。

轮次 结果
try1 正常 345 帧
try2 断网，0 帧
try3–7 服务端每次开播都真的重建管线（旧版只会复用死流）
try8 网络恢复后自动出画，495 帧，1920×1080

全程没重启服务。修复后连测 3 次都是 0.1 秒出 init、约 124 帧/5 秒。

7.2 连接与重连

退避是必要的 —— 服务端重建管线要几百毫秒，前端狂连会把线程池打满。

这里有个隐蔽 bug：onclose 里没把 ws 置空，而 connect() 开头有这么一段：

断开后 ws.readyState 是 3，条件不成立本来没事，但如果重连途中再次触发
connect()（watch 和 onMounted 会连触两次），就会拿到一个半死的 socket。
补上 ws = null 之后逻辑才真正干净。

9. 排障手册

10. 小结

这套链路的核心设计取舍：

  1. 一个 key 一条管线 —— 用引用计数换摄像头并发会话，代价是必须处理死流
  2. caps 是协商不是命令 —— 所以永远要回读实际值，不能信配置
  3. ISP 参数走 REST、视频走 WS —— 互不阻塞，但也不会互相通知
  4. 默认 MSE 不用 WebCodecs —— 牺牲 0.2 秒延迟换 HTTP 环境可用性
  5. unsupported 要显式返回 —— 比返回假值让用户白调半天强

最值得记住的一条：静默失败是最贵的失败。管线错误不 pop、impl_class 配错
走 mock、onclose 不置空 —— 这三个 bug 的共同点都是「看起来一切正常，就是没画面」，
每一个都花了大半天才定位到。
