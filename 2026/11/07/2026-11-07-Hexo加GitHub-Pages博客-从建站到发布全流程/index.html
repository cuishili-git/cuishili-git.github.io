技术笔记

从零搭一套 Hexo + GitHub Pages 博客，并做到一条命令发布

写了几十篇技术笔记散在各处，迟早会想「有个自己的地方存着」。白嫖 GitHub Pages 是最省事的路子：静态站、免费、能绑自己域名、https://<用户名>.github.io 直接就是地址。

但真动手会发现流程比想象的长，坑也不少。这篇把整条路拆成两段讲透：

  • 建站：一次性的，做完就不用再管
  • 发文：每次都做，必须足够短，否则你会懒得写

全文以一套真实在跑的站点为例，命令和输出都是实跑截下来的。你可以对照自己的环境改路径。

0. 先建立心智模型

最需要先说清的一件事：Hexo 和 GitHub Pages 是两个完全独立的东西，它们之间只有一个交接点——一堆静态文件。

三个推论，能省掉大量困惑：

  1. GitHub Pages 不会解析 Markdown。它只会把仓库里的文件当静态资源发出去。所以 .md 必须先在本地变成 .html。
  2. Hexo 不负责托管。它跑完就退出，产出一个 public/ 目录，之后再也不管。所谓”发布”就是把 public/ 弄到仓库里。
  3. 线上仓库里没有你的 .md 源文件。这是最常见的一脸懵：去 GitHub 网页看自己的博客仓库，发现只有 index.html，没有文章源码。因为传上去的是编译产物。源文件在你本地。

全文只记一句话：
写 Markdown → hexo generate 变 HTML → 把 HTML 推到 Pages 仓库 → 完事。

2. 写文章

2.1 文件放哪、叫什么

  • 目录固定 source/_posts/
  • 文件名就是 URL 里的 :title，所以用中文、描述性、别带空格和特殊符号
  • 命名约定 YYYY-MM-DD-标题.md，方便自己按时间排序

2.2 front matter 是什么

每篇文章开头那段被 --- 包起来的 YAML，叫 front matter，是文章的元数据：

字段 作用 不写的后果
title 文章标题 取文件名
date 发布时间，决定排序和归档 取文件创建时间，可能不对
tags 标签，生成 /tags/xxx/ 聚合页 不进任何标签页
categories 分类，生成 /categories/xxx/ 归入 uncategorized

两个细节：

  • tags 和 categories 用 [] 数组写法，不要写成逗号分隔的裸字符串（YAML 里 a, b 是一个字符串，不是两个标签）
  • front matter 后面空一行再写正文，否则第一段可能被吞进 YAML

2.3 让脚本自动补 front matter

手写 front matter 是纯粹的重复劳动，而且容易把日期写错。发布脚本里的逻辑是这样的：

三个设计决定值得学：

  1. 文件开头已经是 --- 就完全不动。保证「手写 front matter」和「脚本生成」两种方式可以共存。
  2. 标题取首个 # 一级标题，然后把那一行从正文里删掉。否则页面上会出现「标题出现两次」——页头一次、正文一次。
  3. 日期取当前时间。所以 Markdown 里不要自己写 # 标题 之外的时间，靠脚本注入更准。

写作约定：文首写一个 # 标题，正文别再重复；标签和分类用命令行参数传进去。

3.3 别被 0 files generated 骗了

如果不 clean、内容也没改直接再跑一次 generate，输出会变成这样：

0 files generated 不是失败。Hexo 会比对 db.json 里记录的文件状态，没变化的就跳过。所以：

输出 含义
N files generated，N > 0 有 N 个文件被（重新）生成，正常
0 files generated 没有任何文件变化，跳过生成，也正常

ERROR 开头 真错误，看报错内容

判断成功的关键不是数字大小，而是有没有 generated 这个词。

也因此，发布脚本里一定是 clean + generate 连着跑——clean 强制全量重建，避免”改了但缓存没刷”这种更隐蔽的问题。

4. 部署：三条路，只有一条走得通

4.1 三条路对比

方式 命令 原理 本文环境可用？
hexo deploy hexo deploy 用 hexo-deployer-git 把 public/ git push 到仓库 ❌ github.com 443 被阻断
手动 git git push 同上，自己 push ❌ 同一个原因
GitHub REST API 自写脚本 调 api.github.com 创建 Git 对象 ✅ 通了

前两种本质上都是 git 协议/HTTPS 到 github.com，通不通取决于网络。第三种走的是 api.github.com，是另一个域名，可能一个通一个不通——这台机器就是这种情况。

先验证一下自己属于哪种：

如果 api.github.com 返回 200，本文方案直接能用。

4.2 为什么不用 hexo deploy 也不用凑

网上教程会告诉你「在 _config.yml 配好 deploy 然后 hexo deploy 一键发布」。这在网络通的情况下确实最省事。但它有两个问题：

  1. 失败信息很难读。它内部包的 git 命令，报 CONNECT tunnel failed, response 502 时你不会立刻知道是网络还是权限。
  2. 强依赖本地 git 状态。要 git init、要配 user.name/email、要处理 .deploy_git 缓存目录——又一个可能出问题的地方。

API 方案的代价是多写 60 行 Python，换来的是零 git 依赖和明确的 HTTP 错误码（401 是 token 错，404 是仓库名错，409 是分支被并发改）。对一个自己用的发布脚本，这个交换很划算。

顺便说：站点目录 F:\hexo-blog 本身并不是一个 git 仓库（没有 .git）。整个方案里它只是「一堆源文件 + 一个 Node 环境」，跟 Git 没有任何关系。目录里那个 .deploy_git 是早期尝试 hexo deploy 的残留，现在完全没用，删掉也不影响。

5.2 Git 对象模型：四步提交法

这是整个方案唯一需要理解的概念。GitHub 的 API 不是在「上传文件」，而是在让你手动拼装一个 Git commit。Git 内部有四种对象：

对象 是什么 类比
blob 一份文件内容的哈希化存储，不带文件名 一份装箱的货
tree 一个目录列表：名字 → blob sha（可以嵌套 tree） 装箱单
commit 指向一个 tree，加上父 commit 和 message 一次发货记录
ref 可变的指针，refs/heads/main 指向最新 commit 「当前版本」标签

细节 说明
base64 编码 API 传二进制内容必须 base64。文本也可以直接 {"content": "...", "encoding": "utf-8"}，但 base64 更省心
路径用 / Windows 天然是 \，必须 replace("\\", "/")，否则 GitHub 上会出现一堆名字带反斜杠的怪文件

先读 parent 再提交 不读 parent 会得到一个孤儿 commit，main 会丢掉历史

5.3 为什么不能传 base_tree（最关键的一个决定）

创建 tree 时有个可选参数 base_tree：给了它，新 tree 就是在旧 tree 基础上增量修改；不给，就是完整替换。

本文脚本的选择是：不给，全量覆盖。

为什么？因为 public/ 是一份完整快照，而我要的结果是「线上仓库 == 本地 public」。如果用 base_tree 增量：

  • 加文章 ✅ 正常
  • 删文章 ❌ 文件会留在线上，因为增量模式不会删除未提及的路径

这就是为什么脚本注释里写着「删掉的文章才会从仓库里消失」。

代价也很明确，必须知道：

仓库是 public/ 的镜像。任何在 GitHub 网页端直接改仓库文件的操作，下次发布会全部被覆盖。

要改内容，改 source/_posts/ 里的 md，重新发布。

5.4 提交信息与 URL

提交信息形如 post: 搞不清V4L2-GStreamer-appsink-一篇讲透 @ 2026-11-07 10:22，在 GitHub 提交历史里一眼能看出是哪篇文章。

URL 里的中文必须 quote() 成百分号编码（%E6%90%9E...），但浏览器地址栏显示的还是中文，复制粘贴没问题。

8. 踩坑复盘

全部是这台机器上真实出现的，按坑的恶劣程度排序。

8.1 hexo generate 静默失败，只打印 help

项 内容

现象 仓库里出现名为 2026\11\07\index.html 之类的怪路径
原因 用 os.path.relpath() 得到的是 Windows 风格 \，直接传给 API
修复 .replace("\\", "/")
教训 任何跨平台的路径字符串，进 API 前先统一成正斜杠

8.9 文档与实际不符

README.md 里写「发布脚本与技能内 scripts/publish.py 同源」，实测不是完全同源（差 8.7 那条）。这类描述性文字最容易过期，改脚本时不会有人记得同步 README。

建议：README 里涉及「两处一致」的说法，要么删掉，要么附一句「以 diff 结果为准」。

9.2 换主题

然后 _config.yml 里 theme: next，重新生成。主题配置在 _config.next.yml 或 themes/next/_config.yml。

换主题会改变 HTML 结构，如果你有自定义 CSS 或注入脚本，需要一起改。

9.3 绑自定义域名

  1. 域名 DNS 加 CNAME 记录指向 <用户名>.github.io
  2. 仓库 Settings → Pages → Custom domain 填域名
  3. GitHub 会在仓库根自动生成 CNAME 文件

注意：全量覆盖部署会把仓库根的 CNAME 冲掉。必须在脚本里也加一个 CNAME blob（跟 .nojekyll 一样处理），否则每次发布都要去网页端重新配一遍。

9.4 加文章但不想现在上线

Hexo 的草稿机制：

_drafts/ 下的东西不会被 generate（除非 --draft）。

9.5 文章里的图片

post_asset_folder: true 会让每篇文章配一个同名目录，图片放进去用相对路径引用。本文这套配置是 false，所以图片建议：

  • 放 source/images/，用 /images/xxx.png 绝对路径引用
  • 或直接外链图床

10. 收尾：这套东西的分层

回头看一眼，其实只有三层，各管各的：

层 组件 职责 出问题时看哪
写作层 source/_posts/*.md 内容 文件在不在、front matter 对不对
生成层 Hexo + 主题 md → html N files generated 那行、public/ 里的文件
分发层 GitHub API + Pages html → 线上 ✓ 已提交 <sha>、HTTP 200

排错的顺序应该是从下往上：先确认网络/API 通（curl api.github.com），再确认 generate 出了文件，最后才怀疑文章内容。反过来做（一上来改 md）是最费时间的。

再记一遍那句话：
写 Markdown → hexo generate 变 HTML → 把 HTML 推到 Pages 仓库 → 完事。

这套方案里唯一”非标准”的地方是第三步走 API 而不是 git。理解了 blob → tree → commit → ref 这四步，你就再也不会被”推送失败”卡住了。
