几个必须知道的细节：

  1. 内核模块目录不是版本化的。/lib/modules/ 下面直接就是 .ko 文件（RTL8821CS.ko、hci_uart.ko、rtk_btusb.ko），没有 6.1.141-xxx/ 这种子目录。所以 modprobe 能用，但 insmod /lib/modules/$(uname -r)/... 这种写法会失败。

  2. 板子上没有 curl，只有 wget。文档里所有 HTTP 探测都用 wget -qO-。

  3. i2cdetect 要 root。普通用户 forlinx 跑会报 Permission denied，得 sudo。

  4. fuser 是 BusyBox 版，只支持 fuser [-msk46] FILE，不支持 -v。

0. 先建立心智模型

0.1 摄像头不是一个”设备”，是一条流水线

新手最容易犯的错，是把 /dev/video0 当成”摄像头”。它不是。
/dev/video0 只是流水线末端的一个取水口。真正的硬件在链条最上游：

对应到 Linux 里的软件对象：

环节 内核里的对象 用户态怎么碰它
感光芯片 V4L2 subdev（/dev/v4l-subdev5） media-ctl、v4l2-ctl -d /dev/v4l-subdev5
芯片寄存器 I2C 设备（3-0036） i2cdetect、i2cget/i2cset
物理层 + CSI V4L2 subdev（rockchip-csi2-dphy0、rockchip-mipi-csi2） 一般不用碰，由驱动自动配
ISP V4L2 subdev（rkisp-isp-subdev） media-ctl 设格式
3A 参数注入 /dev/video29（rkisp-input-params） 写 3A 参数的结构体
输出帧 /dev/video23（rkisp_mainpath） v4l2-ctl、VIDIOC_* ioctl

所以”分析设备上有哪些摄像头”，本质是在 media 拓扑图里数 sensor 实体，而不是数 /dev/video*。

0.2 一台设备上通常有 4 种摄像头形态

形态 典型硬件 谁在用 本文覆盖
MIPI 裸 sensor OV13855 / IMX415 / OS04A10 嵌入式板子板载 重点
USB 摄像头（UVC） 各种 USB 免驱摄像头 桌面、工控机 通用方法
网络摄像机（ONVIF/RTSP） 海康/大华/宇视 IPC 监控现场 重点
私有协议摄像机 厂商 SDK 对接 老项目 只讲判定

四种形态的”控制通道/画面通道”完全不一样，但分析套路是一样的：先找到设备节点，再判断哪个节点搬像素、哪个节点下命令。

0.3 全文只记一句话

Device Caps 里有 Video Capture 的，是画面通道；
只有 Metadata xxx 的，是控制通道。

别用”有没有 Streaming“来判——控制节点也有 Streaming，它流的是参数不是像素。详见 2.4。

2. 分清控制通道和画面通道

2.1 为什么必须分清

因为这两类通道的编程方式完全不同：

  • 画面通道：VIDIOC_REQBUFS → VIDIOC_QBUF → VIDIOC_STREAMON → VIDIOC_DQBUF 循环取帧
  • 控制通道：VIDIOC_S_EXT_CTRLS / VIDIOC_S_FMT / 直接 write() 参数结构体 / I2C 读写

你要是对着一个控制节点去 REQBUFS，会得到 Inappropriate ioctl for device。
你要是对着画面节点去写 3A 参数，什么都不会发生。

2.2 四种形态的通道对照表

形态 控制通道 画面通道 怎么验证控制通
MIPI 裸 sensor I2C（/dev/i2c-3 地址 0x36）+ subdev ioctl（/dev/v4l-subdev5） /dev/video23（ISP 出 YUV）或 /dev/video1（CSI 出 RAW） sudo i2cdetect -y -r 3，0x36 位置显示 UU 或 36
USB UVC USB 控制端点（UVC 标准控制 + 可选 XU 厂商扩展）；部分参数走 /dev/videoN 的 VIDIOC_S_CTRL 同一个 /dev/videoN（等时/批量传输） v4l2-ctl -d /dev/videoN --list-ctrls 有输出
网络摄像机 ONVIF HTTP + SOAP（http://ip/onvif/device_service，端口 80/8000） RTSP（rtsp://ip:554/...） wget 拉 WSDL，或用 onvif 客户端 GetDeviceInformation
私有 SDK 摄像机 厂商 SDK 登录（TCP 私有协议，常 8000/37777） SDK 实时流回调 / RTSP SDK 登录返回 0

2.6 决策树

3. 读懂 media 拓扑图

3.1 三个概念：entity、pad、link

  • entity（实体）：一个硬件模块（sensor、dphy、csi、isp、输出节点）
  • pad（焊盘）：实体的输入/输出端口。SINK 是输入，SOURCE 是输出
  • link（连线）：从某个 SOURCE pad 连到另一个 SINK pad，可以启用（[ENABLED]）或禁用

所以整张图就是数据流的电路图。

要出能看的画面，得走另一条支路——ISP。看 media3：

pad 方向 干什么
pad0 SINK 收 RAW（Bayer 10bit，还是 4224x3136 原始尺寸）
pad1 SINK 收 3A 参数（背后就是 /dev/video29 rkisp-input-params）← 控制通道入口

所以”ISP 是不是在工作”，就看 pad0 有没有 RAW 进来、pad2 的格式对不对。

3.3 [ENABLED] 是陷阱，别当真理

media-ctl -p 里一堆 [ENABLED]，很多人以为”这表示链路通、能出图”。不对。

[ENABLED] 只是当前链路开关状态，是驱动初始化时设的默认值。它不代表：

  • sensor 真的上电了
  • 格式协商成功了
  • 你能 STREAMON

真实判据只有一个：STREAMON 成功并且 DQBUF 拿到帧。

本机就有一个绝佳例子：

两个都是 rkisp_mainpath，都标 [ENABLED]，但 vir0 绑的是当前的 sensor，vir1 是个空壳虚拟设备。去拉 video31 会失败。

4. 协商画面参数

“协商”这个词很准确：你提要求，驱动可能改你的要求，最后以驱动给你看的为准。

4.1 三层分辨率，先搞清楚你在改哪一层

新手常犯的错：想把画面改小，就去改 sensor 驱动里的寄存器。不用。 改 ISP 输出就行，sensor 一直按 4224x3136 出，ISP 帮你缩。

sensor 原生 从哪知道？两处：dmesg 的 s_stream: on: 4224x3136@30，或 media-ctl -p 里 sensor/csi 实体的 fmt:SBGGR10_1X10/4224x3136。

4.3 S_FMT 的”假成功”——本节最重要

VIDIOC_S_FMT 的语义是：驱动会尽量满足你，满足不了就改成它能做的，然后告诉你改成了什么。

它几乎不会返回错误。所以你绝不能假设”我设了 1920x1080，出来的就是 1920x1080”。

参数 建议值 为什么
rc-mode 1（CBR） 监控场景要稳定带宽。VBR 在静止画面时掉到几百 kbps，一动就冲到 10Mbps，网络抖动直接卡死

6.4 产物长什么样

拆开读：

字节 含义
00 00 00 01 Annex-B 起始码（4 字节版），后面跟一个 NAL
09 NAL type 9 = AUD（访问单元分隔符）
00 00 00 01 又一个起始码
67 NAL type 7 = SPS（序列参数集，含分辨率/profile）
64 00 32 SPS 内容：profile_idc=0x64（High）、level=0x32（L5.0）
后面还会有 68 = PPS 图像参数集

这里埋了第 8 节要用的伏笔：起始码 00 00 00 01 是 Annex-B 格式（裸流、文件、RTSP 用这个）。
浏览器要的是 AVCC 格式（长度前缀，装在 MP4 里）。两者需要转封装，不是转码——数据本身不变，只改”怎么标记帧边界”。

7. 服务端：把一路流发给多个人

7.1 浏览器为什么不能直接播裸 H.264

三个硬事实：

  1. <video src="xxx.h264"> 不工作。浏览器要的是容器（MP4/fMP4/TS），裸流没有时间戳、没有索引、没有参数集声明
  2. MediaSource 不认裸流。它只吃 fMP4（ISO BMFF）或 WebM 分片
  3. WebCodecs 需要 avcC 描述（就是 MP4 里的 avcC box，装着 SPS/PPS 的转义版本），不能直接喂 Annex-B 起始码

所以从”H.264 裸流”到”浏览器能播”，中间必须有封装这一步。

7.2 四条技术路线

路线 端到端延迟 实现复杂度 适合 代价
HLS（切片 + m3u8） 3~10 秒 低 能忍延迟的展示 延迟大；要切片器
WebSocket + fMP4 + MSE 1~3 秒 中 绝大多数项目 要做 fMP4 封装
WebSocket + Annex-B + WASM 软解 0.5~1.5 秒 中 延迟敏感、设备性能弱 前端 CPU 高（单路 30~60%）
WebRTC < 0.5 秒 高 对讲、实时操控 信令、ICE、STUN/TURN 全套

给新人的默认建议：WS + fMP4 + MSE。 兼容性最好，延迟能接受，实现量适中。

如果服务端已经只有 Annex-B 裸流、又不想改后端，前端用 jmuxer 这类库在浏览器里现场转封装，也是完全可行的（第 8 节给代码）。

改动 解决什么

10.6 术语表

术语 全称 一句话解释
V4L2 Video4Linux2 Linux 摄像头/视频采集的统一接口，全是一堆 ioctl
subdev sub-device 流水线里的一个硬件模块，不直接出帧，只做配置
media controller — 描述 subdev 之间怎么连的拓扑框架，media-ctl 就是它的工具
entity / pad / link — 模块 / 端口 / 连线，拓扑图三要素
Bayer / RAW — 感光芯片的原始输出，每像素只有一个颜色分量，需 demosaic
demosaic — 把 Bayer 还原成 RGB/YUV 的算法，ISP 的核心工作之一
ISP Image Signal Processor 图像信号处理器，做去马赛克、白平衡、伽马、降噪、锐化
3A AE/AWB/AF 自动曝光 / 自动白平衡 / 自动对焦
IQ 文件 Image Quality ISP 的调参文件（JSON），决定色彩、降噪、曝光策略
MPP Media Process Platform Rockchip 的硬件编解码框架
NV12 — YUV420 的一种内存布局：Y 平面 + UV 交错平面，共 1.5 字节/像素
GOP Group of Pictures 一个 I 帧到下一个 I 帧之间的帧数
IDR Instantaneous Decoding Refresh 能独立解码的关键帧，新客户端必须从它开始
CBR / VBR Constant/Variable Bitrate 恒定/可变码率
Annex-B — H.264 裸流格式，用 00 00 00 01 标记 NAL 边界
AVCC — MP4 内的 H.264 封装，用长度前缀标记 NAL 边界
fMP4 Fragmented MP4 分片 MP4，MSE 唯一认的 H.264 容器
MSE Media Source Extensions 浏览器的 JS 播放接口，MediaSource
UVC USB Video Class USB 免驱摄像头标准
ONVIF Open Network Video Interface Forum 网络摄像机的控制协议，基于 SOAP/HTTP
RTSP Real Time Streaming Protocol 网络摄像机的取流协议
PTZ Pan/Tilt/Zoom 云台转动与变焦

写在最后

如果你是第一次接手这类项目，建议按这个顺序动手，一天能走完：

  1. 上午：跑完第 1、2 节的命令，把设备普查结果写进自己的笔记（节点名册、sensor 型号、I2C 地址、拓扑图）
  2. 中午：跑第 5.2 节的 gst-launch 抓 10 帧，用文件大小验算分辨率是否生效
  3. 下午：把 v4l2_grab.c 编译跑通，改改参数（换成 GREY、换成小分辨率），体会”协商→回读→实际出图”三步
  4. 傍晚：跑第 6.4 节，用 od 看一眼 NAL 头，理解 Annex-B
  5. 收尾：把第 8.1 节的 HTML 存成本地文件，打开看能不能出画面

走完这五步，你对”从摄像头到浏览器”的整条链路就有了肌肉记忆。剩下的问题，基本都能在第 9 节的表里找到入口。

真正难的不是这些命令，是永远先确认前提：

  • 我看到的这个节点，是画面通道还是控制通道？
  • 设备现在有没有被别人占着？
  • 我设的参数，驱动真的接受了吗？画面真的对了吗？
  • 前端连上了，但拿到的是不是一具尸体？

这四个问题问对了，八成的坑在敲命令之前就能避开。
