RV1126B 视频通道实战：v4l2 命令行抓图、录像与 MIPI/ONVIF 双路排查

在 RV1126B（OK1126Bx-S）上做摄像头开发，网页直播、算法推理都封装在平台进程里，但排查问题最终要落到 V4L2 命令行：直接对 /dev/videoX 抓一帧、录一段，把”画面黑了”拆成”哪一层黑了”。本文整理实测可用的 v4l2/ffmpeg 命令、设备节点地图，以及三次黑屏换来的踩坑复盘。

一、设备节点地图：先搞清 /dev/video* 都是谁

板上是 rkisp + rkcif 的流水线，节点非常多，v4l2-ctl --list-devices 一看便知（实测输出节选）：

节点 归属 干什么
/dev/video0 rkaiisp AI ISP 处理
/dev/video23~27,30 rkisp-vir0 mainpath ISP 主输出，dp 平台就吃 video23
/dev/video28,29,36,37 rkisp-statistics 3A 统计数据（AE/AWB 直方图）
/dev/video1~11 rkcif-mipi-lvds CIF 侧原始流（绕过 ISP）
/dev/media0/1/3 media controller 拓扑与链路管理

二、抓一帧看画面（v4l2-ctl 标准三步）

拿到 JPEG 后算平均亮度（Yavg），这是判黑屏的唯一硬标准：黑帧实测 1.97，正常室内 96~140。进程活着、心跳正常、线程数对——都不算数，只有像素算亮度算数。

四、踩坑复盘

坑 1：v4l2-ctl 报 Device or resource busy（EBUSY）

/dev/video23 是平台进程 dp 的地盘。dp 懒加载 mipi worker 后会持有 vb2 队列，即使 /proc/*/fd 里查不到谁占着，驱动侧的会话状态还在，v4l2-ctl 的 S_FMT/REQBUFS 照样 EBUSY（实测两次复现）。正确姿势二选一：

  • 停 dp 再抓：/etc/init.d 停 device_platform → v4l2 随便抓 → 再启动。标准救屏脚本 restart_camera.sh 的 [1/4] 步就是干这个的；
  • 别和 dp 抢：临时验证优先用平台的抓帧能力（流程 snapshot 节点返回 dma_fd；ONVIF 通道自动落 snapshots/*.jpg），SFTP 拉回来算亮度，零冲突。

坑 2：判黑屏只认 Yavg，其他全是参考

有流 13 线程、无流 8~9 线程都正常；心跳、GET/STATE 正常也不代表画面活。曾把 9 线程当故障折腾半天，最后抓帧一算亮度 138——画面本来就好的。判据优先级：抓帧 Yavg > API 回包 > 线程数。

坑 3：双通道分不清，白忙一场

平台同时存在本地 MIPI（vch_1）和 ONVIF 网络通道（vch_tki_device_*，RTSP 拉流）。网络摄像头 RTSP 服务时好时坏（实测连报 7 次 Could not open resource for reading and writing），网页黑屏时先确认看的是哪一路——那 7 次错误全是网络路的，本地 MIPI 无辜。

坑 4：SSH 里 sudo 卡死

非交互 SSH 通道里 sudo 脚本 会停在密码提示直到超时，必须 echo <密码> | sudo -S <命令>。

五、命令速查

小结

v4l2 命令行是把”黑盒平台”拆开看的螺丝刀：--list-devices 建地图、--stream-mmap 抓帧验活、ffmpeg + h264_v4l2m2m 硬编录像。三条纪律：判活只认 Yavg；video23 别和平台进程抢；黑屏先分清 MIPI 还是网络通道。
